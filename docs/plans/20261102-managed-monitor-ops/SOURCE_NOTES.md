## External primary guidance

- [Microsoft: Named Pipe Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights): explicit pipe security descriptor matters; default DACL is **not user-only**, can grant broader read rights. Therefore native Windows ACL construction and tests are mandatory. Source may redirect by locale; English canonical URL used here.
- [Microsoft: Named Pipes](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipes): pipes can be accessible across network; specifically deny network access or use a local-only IPC alternative. This justifies rejecting remote pipe clients.
- [Microsoft: CreateNamedPipe](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createnamedpipea): `SECURITY_ATTRIBUTES` controls named pipe security descriptor. The implementation should use Unicode variants and platform-appropriate language bindings where possible.
- [Python: multiprocessing.connection](https://docs.python.org/3/library/multiprocessing.html#module-multiprocessing.connection): `AF_PIPE` supports Windows pipe clients/listeners; the `recv()` object path unpickles data, unsuitable for untrusted input. Standard `authkey` HMAC alone does not replace required OS pipe ACLs. Prefer strict byte-oriented JSON framing and explicit identity.
- [Uvicorn: Server Behavior](https://uvicorn.dev/server-behavior/): TCP accept queue/backlog and graceful shutdown behavior. Readiness must be tied to real bound/listening socket plus application startup, not printed text prior to `server.run()`.

## Research/design decisions and uncertainty

1. Prefer scoped short-lived local capabilities over browser-session-cookie handoff. This is an architecture choice, **not existing behavior**; scope minimization and reduced secret persistence are the rationale.
2. Separate host service health from agent execution-context access. WSL2 and Docker namespaces do not automatically inherit Windows named pipe permissions; implementing bridges is beyond this plan.
3. Lifecycle reuse of Runmux patterns is grounded in source; direct imports/reuse of its package are intentionally **not prescribed** until Phase 00 checks dependency semantics.
4. A proper Windows SID-restricted pipe requires supported native API access; choice of package/binding, privilege model and exact ACL SDDL to be decided against installed dependencies and verified Windows tests before code review. Do not substitute default ACLs for speed.
5. Recent GitHub commits on 2026-11-02 and in-flight agent work may make some proposed changes already complete. Phase 00 must audit and **skip completed stages** rather than creating duplicative work.
6. No source beyond user-provided incident details establishes whether the stop-command agent is currently active or whether the live Monitor is healthy. This cannot be inferred from public branches/PRs.
