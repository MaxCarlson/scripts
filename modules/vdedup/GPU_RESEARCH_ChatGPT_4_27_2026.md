# GPU Modernization Strategy for vdedup

## What the repo is doing today

The current `vdedup` codebase already has the right *shape* for a staged deduplication system that can preserve your `-q` workflow. The real execution path is: Q1 size bucketing, Q2 exact hashing, Q3 metadata clustering, Q4 pHash, Q5 scene fingerprints, Q6 audio fingerprints, and Q7 timeline fingerprints. The CLI’s current `-q/--quality` behavior is no longer “cumulative presets” by default; single digits select a single stage, while ranges like `1-4` or `1-7` combine stages. The tests also show that stages 5, 6, and 7 are already expected to run independently. That matters, because your requested design goal maps well onto the code as it exists now. fileciteturn0file1

There are also a few integration-critical inconsistencies inside the repo that any plan should treat as bugs in documentation, not as intended architecture. In particular, `pipeline.py` still says stage 5 is a no-op in its module docstring, but the implementation clearly runs scene fingerprinting there; the older repo research notes also describe an earlier quality mapping that no longer matches the current CLI. So the source of truth for any future work should be the current implementation and tests, not the older internal notes. Gemini’s memo is directionally right about the main bottlenecks, but some of its assumptions should be updated to match the live code. fileciteturn0file1 fileciteturn0file0

The most important architectural problem is not GPU-related: Q3 currently emits metadata-only groups as if they were duplicate groups, and then excludes those files from later visual stages. In practice, that means Q3 can create false positives *and* reduce recall for Q4–Q7 by preventing later verification. The repo’s own analysis documents this failure mode explicitly, and the pipeline code confirms the exclusion behavior. If you keep the current destructive Q3 semantics, a faster GPU path will make the system faster but not fundamentally more correct. fileciteturn0file1

## Where your 5090 can actually help

Your current `--gpu` path is only a partial hint to `ffmpeg`. In `phash.py`, the code adds `-hwaccel cuda`, but it still extracts frames to temporary PNG files, reopens them with PIL, and computes hashes with CPU-side `imagehash`. In other words, decode may touch the GPU, but frame transport, image materialization, and hashing still bounce through the CPU and filesystem. Q2 hashing and Q3 `ffprobe` metadata probing also remain entirely CPU and process-spawn driven. That is why a big card like your 5090 will currently be underutilized. fileciteturn0file1

The right way to use a 5090 is to move the expensive *video* work onto the GPU, not to try to force every stage onto CUDA. entity["company","NVIDIA","gpu vendor"]’s Video Codec SDK exposes NVDEC/NVENC as dedicated hardware engines, separate from the normal compute path, and the SDK documentation specifically describes keeping frames in GPU memory so that decode and GPU compute can run as one pipeline. NVIDIA also notes that Blackwell improves media capability, including higher H.264 decode throughput and added 4:2:2 decode support for H.264 and HEVC. The RTX 5090 product page confirms the card is a Blackwell GPU with 32 GB of GDDR7, which is more than enough VRAM for aggressive batched frame sampling and multi-stage descriptor extraction. citeturn0search1turn0search6turn11search0turn0search3

For Python specifically, the strongest fit is PyNvVideoCodec, which NVIDIA positions as the official successor to VPF. It supports Windows, Linux, and WSL, supports Blackwell GPUs, installs from PyPI, and exposes decoded frames through DLPack. Its `SimpleDecoder` is the right tool for sparse random-access sampling, while `ThreadedDecoder` is designed for high-throughput sequential pipelines with background prefetch. Because PyNvVideoCodec frames implement `__dlpack__`, they can be turned into Torch tensors with `torch.from_dlpack()` while sharing memory instead of copying it. That is the key building block your current implementation is missing. citeturn4search0turn4search2turn1search1turn1search2turn0search5turn2search0

If you need a fallback backend, official NVIDIA FFmpeg guidance is still useful, but it is a fallback, not the end state. NVIDIA’s FFmpeg documentation recommends `-hwaccel cuda -hwaccel_output_format cuda` when you want frames to remain on the GPU. Your current path only uses the first half of that pattern. Even with that fixed, a CLI-FFmpeg pipeline is still less attractive than PyNvVideoCodec for your use case because your repo does a lot of random or semi-random frame access and wants Python-native integration, caching, and stage-specific reuse. citeturn0search0turn4search4

## The q-level redesign that preserves your structure

The cleanest way to keep your current program shape is to treat each `-q` stage as a detector with its own backend, its own cache entries, and its own report output. The important change is that only *safe* stages should be deletion-ready by default. That yields a structure like this: Q1 candidate bucketing, Q2 exact-duplicate proof, Q3 metadata candidate generation, Q4 coarse visual duplicate/subset detection, Q5 scene-aware visual detection, Q6 audio corroboration or rescue, and Q7 dense overlap verification. This preserves your “early cheap narrowing, later slow verification” design while still allowing every stage to run alone. fileciteturn0file1

Q1 should stay cheap and broad. It is useful for narrowing search space, but same-size files are not evidence of duplicate content. If you want Q1 to be independently runnable, it should emit a *candidate* report, not a delete-ready duplicate report. That can still fit your current JSON shape if the `method` and `evidence` payload make the distinction explicit, but it should not be auto-applicable. Q2 can remain your first truly safe stage because it only emits groups after full-file hash equality. fileciteturn0file1

Q3 should be demoted from “duplicate detector” to “candidate generator.” That is the single highest-leverage correctness fix in the repo. Metadata similarity is useful for blocking, scheduling, and prioritization, but not for final decisions. The current repo research note is correct on this point: Q3 should not poison Q4+ by excluding accepted members before visual verification. In a combined run, Q3 should create candidate edges or buckets that later stages verify. In a Q3-only run, it should still produce a report, but the report should be clearly marked as candidate-level evidence. fileciteturn0file1

Q4, Q5, and Q7 are where the 5090 should earn its keep. Q4 should become the low-cost GPU visual stage: sparse uniform frame sampling, batched GPU pHash or similar compact descriptors, then cheap candidate generation from those signatures. Q5 should remain scene-aware and focus on clip-style or edited-content robustness. Q7 should become the dense verifier and localizer. That design is well aligned with the public research landscape: VCDB was built specifically for partial copy detection with real copied segments; VCSL extends that idea to much larger, segment-level localization; and ViSiL’s results support the same core intuition your repo already hints at—that fine-grained frame-to-frame similarity and temporal alignment are stronger than coarse global video descriptors when you care about overlap, clips, and re-edits. citeturn8search0turn9search3turn7search2

## The backend I would actually integrate

The most practical integration path is to add a narrow decode-and-descriptor backend layer without changing your report model or stage orchestration. Concretely, add a backend module that exposes a small, stable interface such as: “sample indexed frames,” “sample uniform timestamps,” “stream sequential frames,” and “extract mono audio.” Then provide three implementations: CPU legacy, FFmpeg-CUDA fallback, and PyNvVideoCodec-CUDA primary. `pipeline.py` keeps calling stage helpers; the helpers stop shelling out to PNG-oriented code and instead request tensors from the backend. That preserves the current repo structure instead of forcing a rewrite. fileciteturn0file1 citeturn4search0turn1search1turn1search2

For sparse stages such as Q4 and most of Q5, use PyNvVideoCodec `SimpleDecoder` with `use_device_memory=True` and indexed frame retrieval. For dense sequential stages such as Q7, use `ThreadedDecoder` so that decode is prefetched while your GPU computes descriptors. Convert frames with `torch.from_dlpack()`, keep them in CHW/RGBP form, and do resize, grayscale/luma conversion, normalization, and descriptor computation directly in CUDA tensors. CV-CUDA is optional but useful if you want high-quality GPU resize and fused image preprocessing operators; otherwise, plain Torch tensor ops are enough for the first integration. citeturn1search1turn1search2turn0search5turn2search0turn3search1turn3search2

For the actual visual descriptor, I would not keep PIL + `imagehash`. The best low-risk improvement is a batched GPU pHash implemented in Torch: convert to luma, resize to a small fixed resolution, apply a batched low-frequency transform, threshold local coefficients, and pack the result into 64-bit fingerprints. The exact math is an implementation choice, but the important architectural change is that the whole Q4/Q5/Q7 descriptor path stays on the GPU until you are ready to cache or compare compact signatures. With your 5090, batched descriptor extraction will be far more important than merely toggling FFmpeg decode flags. This is an implementation inference built on the official zero-copy decode and tensor-interoperability pieces above. citeturn0search5turn2search0turn3search2

For Q7 specifically, your repo already contains the strongest upgrade path: `compute_video_fingerprint`, `PHashIndex`, and `SequenceMatcher` are all present, and the tests already validate diagonal-streak overlap behavior. Today’s main pipeline still uses simpler tuple-based alignment logic. I would make Q7 the stage that formally adopts the `VideoFingerprint -> PHashIndex -> SequenceMatcher -> localized overlap` path, because that gives you start/end localization and a cleaner definition of duplicates vs subsets vs partial overlaps. It also matches the benchmark direction set by VCDB and VCSL. fileciteturn0file1 citeturn8search0turn9search3

## What to accelerate first and what to leave alone

Q4 and Q7 should be first. They are the stages where decode, frame materialization, and descriptor extraction dominate runtime, so moving them to NVDEC + zero-copy Torch tensors gives the largest upside. Q5 is next, because scene-aware sampling still benefits substantially from GPU decode and batched descriptor extraction. Q2 should mostly stay CPU-side because it is storage and file-I/O dominated; the 5090 does not make SHA-256 or BLAKE3 over disk reads magically efficient in the same way it helps sampled visual analysis. Q3 should be simplified for correctness before it is optimized. fileciteturn0file1

Q6 is different. Audio can be GPU-accelerated with Torch/torchaudio signal transforms, and Torch audio transforms can run on CUDA, but that is not where I would spend effort first. The bigger opportunity is to use Q6 as corroborating evidence or a rescue stage for cases where visuals are degraded by crops, overlays, heavy compression, or blank/low-motion content. In other words, Q6 should become *higher-value evidence*, not necessarily the first big GPU project. citeturn10search1turn10search0turn10search5

## Validation and rollout criteria

This work should be judged on two axes: correctness and throughput. On correctness, use your own regression tests plus public partial-copy benchmarks. VCDB is still a strong reality check for partial copy detection, and VCSL is the more important benchmark for modern segment localization because it is much larger and explicitly annotated at the copy-segment level. On throughput, compare three concrete paths: the current temp-PNG CPU path, an FFmpeg-CUDA fallback path, and a PyNvVideoCodec+DLPack GPU path. Measure end-to-end stage time, not just decoding speed, because the current bottleneck is the whole decode-to-descriptor chain. fileciteturn0file1 citeturn8search0turn9search3turn4search2

The rollout standard I would use is simple. Q2 remains safe-to-apply. Q3 becomes non-actionable candidate output. Q4 and Q5 can become actionable only after you measure their precision on your own library and on a public partial-copy benchmark. Q7 should become the highest-confidence non-exact stage and the default verification stage for any combined run that includes it. That gives you a coherent interpretation of `-q`: lower levels are faster and broader, higher levels are slower and safer, and every level can still run independently and write a report in the same overall format. fileciteturn0file1

## Open questions and limitations

The repo already contains multiple overlapping research directions, and not all of them are internally consistent. The biggest unresolved question is how you want to distinguish “candidate-only” reports from “safe-to-apply” reports in the JSON and apply path. The current report writer preserves method/evidence payloads, which helps, but it does not yet enforce an explicit safety contract by detector type. That is a correctness issue you should settle before integrating faster GPU stages. fileciteturn0file1

The second open question is whether you want Q7 to stay pHash-based or to evolve toward richer learned descriptors. The research literature strongly supports fine-grained spatio-temporal matching for overlap detection, but the most advanced approaches are more complex than your current repo and may be harder to preserve within the present code shape. My recommendation is to first modernize decode, transport, batching, and overlap verification using the code you already have, and only then decide whether a learned descriptor stage is worth the extra maintenance cost. fileciteturn0file1 citeturn7search2turn9search3
